# WB/Ozon Reseller Bot

Production-ready Telegram-бот для автоматизации работы реселлеров Wildberries и Ozon.
Бот заменяет менеджера, который вручную принимает заявки на выкуп товаров с кэшбэком,
контролирует статусы заявок и выплаты.

> **Статус проекта:** ✅ разработка завершена. Реализованы все 12 этапов
> запланированного плана. Бот полностью функционален: от каталога товаров
> до автоматических уведомлений о выплатах, включая полноценную
> административную панель.

## Установка и запуск (Docker)

1. Скопируйте файл переменных окружения и заполните реальными значениями:

   ```bash
   cp .env.example .env
   ```

   Обязательно укажите:
   - `BOT_TOKEN` — токен бота, полученный от [@BotFather](https://t.me/BotFather)
   - `BOT_ADMIN_IDS` — Telegram ID администраторов через запятую
   - `POSTGRES_PASSWORD` — надёжный пароль базы данных

2. Соберите и запустите контейнеры:

   ```bash
   docker compose up --build -d
   ```

   Миграции базы данных применяются автоматически при старте контейнера
   `bot` (см. `docker-entrypoint.sh`) — отдельно вызывать `alembic upgrade
   head` не требуется.

3. Проверьте логи запуска:

   ```bash
   docker compose logs -f bot
   ```

Бот полностью рабочий и реализует весь бизнес-процесс из ТЗ от начала до
конца: отправьте `/start`, чтобы увидеть главное меню пользователя.
«📦 Каталог» → оформление заявки (артикул, скриншот заказа) →
администратор одобряет заказ в панели управления → пользователь
подтверждает получение товара → выбирает/добавляет реквизиты → отзыв
и/или чек (если требуются для товара) → ожидание выплаты →
администратор отмечает выплату произведённой → пользователь получает
уведомление. Все разделы меню («📋 Мои заявки», «💳 Реквизиты»,
«📖 Инструкция», «💬 Поддержка») полностью реализованы.

Если ваш Telegram ID указан в `BOT_ADMIN_IDS`, отправьте боту команду
`/admin`, чтобы открыть панель администратора. Полностью реализованы:
«📦 Товары» (создание мастером, редактирование, скрытие/показ, остаток,
удаление), «📋 Заявки» (очередь на проверку со скриншотом заказа,
одобрение/отклонение/запрос повтора — каждое решение сразу уведомляет
пользователя), «💰 Выплаты» (список ожидающих исполнения, отметка
оплаты) и «📊 Статистика» (сводка по пользователям, товарам, заявкам и
выплатам). Раздел «⚙ Настройки» остаётся заглушкой — он не был
детализирован в исходном ТЗ.

Планировщик APScheduler ежедневно (время задаётся переменными
`SCHEDULER_PAYMENT_CHECK_HOUR`/`_MINUTE`) проверяет заявки в статусе
ожидания выплаты с наступившей расчётной датой и присылает
администраторам сводку в личные сообщения с ботом.

## Миграции базы данных

Схема базы данных описана моделями SQLAlchemy в
`src/infrastructure/database/models/` и версионируется через Alembic.
Контейнер `bot` применяет все неприменённые миграции автоматически при
каждом запуске (см. `docker-entrypoint.sh`), поэтому в обычной работе
вызывать команды ниже вручную не требуется — они пригодятся для
локальной разработки или ручной диагностики.

Применить миграции к запущенному в Docker контейнеру PostgreSQL вручную:

```bash
docker compose up -d postgres
docker compose run --rm bot alembic upgrade head
```

Либо локально (при активном виртуальном окружении и доступной БД):

```bash
alembic upgrade head
```

Создать новую миграцию после изменения моделей:

```bash
alembic revision --autogenerate -m "описание изменений"
```

Откатить последнюю миграцию:

```bash
alembic downgrade -1
```

## Локальный запуск без Docker (для разработки)

1. Создайте виртуальное окружение и установите зависимости:

   ```bash
   python3.13 -m venv .venv
   source .venv/bin/activate
   pip install -e ".[dev]"
   ```

2. Скопируйте `.env.example` в `.env` и заполните значения.

3. Запустите точку входа:

   ```bash
   python -m src.main
   ```

Проект разрабатывается строго поэтапно. Каждый этап оформляется отдельным
самодостаточным ZIP-архивом:

1. ✅ Инициализация проекта (конфигурация, логирование, Docker)
2. ✅ База данных: модели SQLAlchemy, Alembic
3. ✅ Domain-слой: доменные сущности, исключения, enums
4. ✅ Репозитории (интерфейсы + реализации)
5. ✅ Application-слой: DTO и сервисы
6. ✅ Bot core: DI, middlewares, фильтры
7. ✅ Пользовательский бот — часть 1 (меню, каталог, начало заявки)
8. ✅ Пользовательский бот — часть 2 (продолжение заявки, реквизиты, поддержка)
9. ✅ Админ-бот — часть 1 (товары)
10. ✅ Админ-бот — часть 2 (заявки, выплаты, статистика)
11. ✅ Планировщик APScheduler
12. ✅ Финализация и полная интеграционная проверка

## Известные ограничения и осознанные компромиссы

Честно документируем решения, принятые в ходе разработки, чтобы не
создавать ложных ожиданий:

- **Редактирование товара** запрашивает все поля заново, а не только
  изменённые — упрощение мастера в пользу единообразия кода создания и
  редактирования. Технически несложно доработать до частичного
  редактирования отдельных полей.
- **Раздел «⚙ Настройки»** в админ-боте — заглушка. Он не был
  детализирован в исходном техническом задании; реализация оставлена на
  усмотрение дальнейшего развития (управление списком администраторов,
  банков и т.д.).
- **Справочник банков** заполняется миграцией `0003_seed_banks` восемью
  крупнейшими российскими банками. Управление списком банков через
  интерфейс бота не реализовано — при необходимости редактируется
  напрямую в таблице `banks`.
- **Фотография товара** — одна на товар (соответствует формулировке
  исходного ТЗ "фотографию" в единственном числе), хотя структура данных
  (`ProductPhoto`, `photo_file_ids`) уже поддерживает несколько фото на
  товар при необходимости расширения.
- **`receipt_required`** — поле товара, добавленное в процессе
  разработки (миграция `0002`): в исходном ТЗ у товара было только поле
  «требуется ли отзыв», однако сам процесс заявки явно описывает
  независимый условный шаг «если нужен чек — отправляет ссылку», для
  которого не было соответствующего поля. Добавлено как логичное
  дополнение, обнаруженное при сквозной реализации бизнес-процесса.
- **Троттлинг** реализован в памяти процесса (без Redis) — корректно
  работает для одного инстанса бота; при горизонтальном масштабировании
  на несколько инстансов потребует переноса на Redis.
- Тесты (`tests/unit`, `tests/integration`) как отдельная директория не
  создавались — вместо этого на каждом этапе бизнес-логика проверялась
  через временные интеграционные скрипты с in-memory реализациями
  репозиториев. Структура `pyproject.toml` (pytest, pytest-asyncio) уже
  готова для добавления постоянного набора тестов.
